Tower · Spec · Break-glass debug access

Looking inside a production pod, without ever handing out exec

Tower's write actions are delegated and reviewed, so pod exec was never going to be a standing feature. But mid-incident an owner sometimes needs a process list, a DNS lookup from the pod's network, or a file the app wrote, and no log line answers it. This is the spec for doing that safely: short, approved, recorded, and enforced by the cluster itself.

Built · live on both clusters

Never exec on Flight. Two debug modes, a second person, and a recording of every byte.

  • Copy mode debugs a copy of the pod that takes no traffic. Live mode adds a debug container to the running pod, for problems a copy can't reproduce.
  • On Flight, a second person approves. An admin can "break the glass" alone, and that session is broadcast and owes a review.
  • Every guardrail that matters is an admission policy, so it holds even if Tower is wrong.

A debug container is safer for these reasons, not inherently. Run as the app's user with a shared process namespace, it reaches the same secrets as exec. So process access is a separate, explicit option that the approver sees.

The flow

Guardrails that don't trust the portal

The first build used fail-closed Kyverno policies on Flight too. On the dev cluster they made break-glass unavailable every time Kyverno lost its lease on a busy node, and on Flight that would happen during the incident itself. So Flight validation moved to built-in ValidatingAdmissionPolicy, and a slim Kyverno keeps only the two jobs it's uniquely good at: the cleanup TTL and the debug image's signature check.

How it was tested

The last piece is a plan for walking every feature in a browser with two people, one an admin and one an app owner, on a Skyport app's Ground and Flight environments. It covers the things a harness can't: the approval round trip, the notification deep links, a sensitive recording refused to the wrong person, and a "glass broken" session reviewed by someone else.
