No stored AWS key for cloud deploys

Hangar reached AWS with two access keys: passwords for machines that worked from anywhere until someone deleted them, one of them shared by every app. I wanted them gone, not rotated. Doing that also turned up a way for Crossplane to make itself an AWS administrator, and the switch itself deleted a function before I fixed the composition that allowed it. This page explains all three for someone meeting these ideas for the first time.

Lambda keyless · Oct 16, 2026

Crossplane and Lambda deploys keep no AWS key.

  • Earned, not stored. A pod proves who it is with a token Kubernetes signed for it minutes ago, and AWS trades that for one hour of access.
  • One function, one role. Each Lambda function gets its own deploy role. One app's pipeline can't touch another app's function.
  • Only the deploy step. Every other pipeline step, including the ones that run the app's own code, has no AWS access at all.
  • A ceiling on everything Crossplane creates. It can no longer create a role without a permissions boundary attached.

Why: two keys that never expired

Hangar uses AWS in two ways. Crossplane builds what an app needs there: an image registry, a Lambda function, a public web address for it. Glidepath, the delivery pipeline, then ships each new version of the app's code into that function. Each needed an AWS identity, and each got an access key: a username and password for a machine.

A key like that has three problems. It never expires, so a leaked copy works until someone notices. It works from anywhere, so a copy on a laptop is as good as the original. And the deploy key was shared by every app, so a leak from one app's pipeline reached every other app's functions. Rotating keys shortens the window; it doesn't close it.

How it works, in plain terms

Think of a building with a front desk. The old way handed each contractor a master key to keep. The new way gives them nothing to keep. They arrive with a badge their employer printed that morning, the desk checks it against the employer's published sample, and hands back a visitor pass for one floor that expires in an hour.

The employer is the cluster: Kubernetes gives every pod a signed identity card, a ServiceAccount token. The published sample is kiac-dev's public signing keys, at hangarplatform.dev/oidc/kiac-dev: anyone can check a signature with them, nobody can make one. The front desk is AWS STS, which checks the token against an IAM role's rules about who may use it, and returns credentials that last an hour. The industry name is web identity federation; on Amazon's own Kubernetes service it's called IRSA.

Decision

The target creates each deploy role

The Lambda target already creates the function, its registry and its execution role, so it creates the deploy role beside them and deletes it with them. A new app needs no IAM step at all.

Decision

A dedicated ServiceAccount

Every pipeline step runs as pipeline-runner, including tests that run the app's own code. Only the deploy step and the bootstrap Job run as glidepath-cloud-deployer, the one subject the role trusts.

Decision

The account, stated once

The AWS account lives in the fleet's clusters.yaml. The compositions and every app's chart read it from there; no app repeats it in cicd.yaml.

What checking the permissions turned up

Finding 0.1

Crossplane could mint an administrator

Its policy let it create any role ending in -exec, decide who may use it and attach any rules. Together that's a way to create a full administrator. Apps couldn't reach it, but a bug in a composition could.

Phase 0

A ceiling on every created role

A permissions boundary caps a role whatever its own rules say. Crossplane's policy now refuses to create a role, or add rules to one, unless the boundary is attached, and nothing may remove it.

Finding 0.2

Labels could be forged

Kubernetes lets any pod use any ServiceAccount in its namespace, and labels on a pipeline run are copied onto its pods. So the admission policies decide by who created the pod, which Kubernetes records and a client can't fake.

The migration

Switching every app at once would break any deploy that runs before its role exists, so for the switch the deploy step kept the old key as a fallback and logged which path it took. Once every app had deployed through its role and no cluster held an AWS key any more, the fallback was removed (phase 4). Now a deploy either assumes its role or stops and says what is missing.

The incident: the switch deleted a function

Crossplane works by comparison: each time it looks at an app, it lists what should exist and deletes anything no longer on the list. Phase 1 made the bootstrap Job wait for the new deploy role. For one pass the role didn't exist, so the finished Job dropped off the list and was deleted. An older rule said the function exists only once the Job has succeeded, so on the next pass the function, its URL and its permission dropped off too, and were deleted in AWS. They came back six minutes later from the placeholder image, with a new web address.

The fix keeps anything that already exists on the list, whatever happens to the conditions it was created under. Two new tests replay both steps; run against the old composition, they fail the way production did.

A condition may decide when to create something. It must never decide whether to keep it.
