Glidepath against the everyday software lifecycle

I wanted to know how Glidepath holds up against the delivery tools most teams already use, so I read it the way a reviewer would: the code, the ADRs and the docs, across every repo it touches. Each finding below says whether it holds today, so a design that is built is never mistaken for one that is enforced.

Strong merge to prod · governance advises

Strong on the road from merge to production, by design. Thin on the developer's inner loop. Most of its governance advises today rather than enforces.

  • The pull-only boundary between clusters is sound: nothing on dev holds prod credentials, and prod only changes from a merged commit.
  • Gates, approvals and test results exist on paper, but on GitHub Free nothing stops a change that skips or fails them.
  • Everything that makes delivery observable and governable runs on one dev cluster.

The change road, as built

A developer writes one cicd.yaml. Pipelines-as-Code starts the first stage from a GitHub webhook, and every later stage starts on the previous stage's CDEvent through a broker that authenticates with the pod's own ServiceAccount token. Ground environments get a direct bot commit. Flight environments only change when a PR on gitops-<app> merges and that cluster's Argo CD pulls it.

Where the control plane lives

The pull model between clusters is sound: nothing on dev holds prod credentials, and prod only changes from a merged commit. Everything else that makes delivery observable and governable runs on the dev cluster.

Strengths

Holds · ADR-0017 · cicd.schema.json

A real paved road

One validated file, scaffolded rather than hand-written. Developers never write Tekton, and preflight rejects a bad config before anything runs.

Holds · image-signing.md

Supply chain beyond the norm

Tekton Chains signs keylessly through a self-hosted Fulcio and Rekor, Conforma checks the provenance, SBOMs are cosign attestations, and Semgrep fails closed when on.

Holds · ADR-0005 · ADR-0004

Sound GitOps trust

Each upper cluster runs its own Argo CD and pulls. The GitHub App key stays in one namespace, and a broker mints tokens for one repo at a time.

Holds · glidepath-relay

Observable by design

One OTel trace per flow across separate PipelineRuns, CDEvents throughout, a release state machine fed by Rollout facts, and stall detectors.

Holds · tower/docs/deployments.md

Day-2 tooling in Tower

Plain-language deployment diagnosis, Rollout controls, rollback as a PR, config edits as PRs, and a recorded break-glass shell anchored in Rekor.

Holds · known-gaps.md

A candid engineering record

25 ADRs, a known-gaps log with evidence for each entry, stubs labelled as stubs, and live runs kept apart from render-only checks.

Weaknesses

Gap

Enforcement

  • Required checks and approvals do not block a merge on GitHub Free.
  • Security gates are opt-in and default off. The release SAST gate treats a scan that never ran as a pass.
  • No secret, dependency or license scanning.
Gap

CI flexibility

  • A fixed four-stage graph: no custom steps, no matrix, no conditional jobs.
  • Build images limited to Node, Java, Python and Go, on floating tags.
  • No build secrets or custom build args, so private package registries are out.
  • The dependency cache covers npm, yarn and Maven only.
Gap

Feedback

  • Chained stage results go to Slack, Backstage and Tempo, never to the PR.
  • No test reports, no coverage, no flaky-test handling.
Gap

Lock-in and drift

  • Hardcoded to GitHub, GHCR and a main default branch.
  • The build relies on kaniko, whose upstream project is archived. amd64 Go builds crash under emulation.
  • The guardrail list, the ruleset and the toolbox schema are kept in sync by hand (gap 35 broke every deploy.target user).
Gap

Isolation

  • Test runs copy the app's secrets into the shared testkube namespace, next to developer-written TestWorkflow YAML.
  • Extra .tekton/*.yaml files in an app repo would run as the pipeline identity, outside the platform's control.
Gap

Operations

  • The dev cluster carries Tekton, the broker, release records, DORA and prod's secrets (Figure 2).
  • Tower's per-action authorization is two weeks old and lives in a separate repo.

What to do next, in order

1. Make the gates real before adding features

Move to a GitHub plan that enforces rulesets, or add a pre-merge admission check or merge bot. Generate the ruleset from releaseGuardrails. Fail Flight releases when gate evidence is missing.

2. Close the loop on the PR

Post every chained stage as a GitHub check, parse JUnit and coverage, and fail the test stage when no test exists.

3. Turn on progressive delivery

Scrape ingress metrics, make an analysis with no data fail, ship a default multi-step canary, and start production on staging health instead of PR open.

4. Fill the everyday CI gaps

Glob matching on push, cron and manual triggers, PR path filters, build secrets and args, monorepo support, and a sanctioned custom-step hook.

5. De-risk the platform itself

Split the control plane from the dev workload cluster, give prod its own secrets path, add a CI check that the schema matches the toolbox image, and plan a BuildKit or Buildah replacement for kaniko.

How this was read

I read code, ADRs and docs across glidepath, tower, airframe, apron and hangar. The highest-impact findings (push-branch matching, Testkube secret copying, the always-pass gates, the inert canary, the DORA labels) were checked directly in source. Nothing was run against a cluster; live behaviour comes from the repos' own verification notes.

Glidepath is about two months old, and its September 27, 2026 architecture review withholds production approval. So read the gaps as a roadmap, not a verdict on the design.
