A Glidepath API for people, Tower and agents

Airframe has a front end an agent can use cold. It has a schema, a contract that says what every kind returns and how it fails, a validator, a verifier, and a gateway that decides what an agent may touch. Glidepath has none of that. What it has is about sixty routes inside Tower's backend that answer every CI/CD question and take every CI/CD action, for Tower alone. This spec moves that surface into Glidepath, builds it the way Airframe is built, and lets Tower and agents share it.

Proposed · Oct 25, 2026

Glidepath gets a contract, a validator and an API, and Tower becomes one of its clients.

  • Durable changes stay git commits. Editing cicd.yaml, promoting, rolling back and pinning all open a pull request. Only short-lived things, such as a re-run or a preview environment, are API calls.
  • Agents may edit cicd.yaml by pull request, limited by field. The whole-file block goes. Each field is open, tighten only or human only, and both Clearance and CI enforce that.
  • Four tiers. Read, reversible in Ground, propose for Flight, never. A human merge is the only thing that changes a Flight environment.
  • Tower moves side by side. Every Tower route stays. Behind each group of routes a switch goes from direct to shadow to api, and flipping it back undoes the move.
  • Glidepath stays standalone. The API ships in glidepath-control-plane and has no Hangar dependency. Tower and Clearance are only clients.

Why: Glidepath answers to Tower, and only to Tower

Airframe's API is its schema. Twenty kinds in catalog.hangar.io/v1alpha1, a versioning policy, and a sidecar per kind that lists what the kind returns, the conditions it reports with a fixed set of reasons, how to verify it and how it is known to fail. All of that is generated into one contract file. An agent asks airframe-capabilities what it can do, runs airframe-validate before it opens a pull request, and runs airframe-verify afterwards. Clearance decides which of those writes the agent may make at all.

Glidepath has the schema half: cicd.yaml and cicd.schema.json. Everything an agent needs at run time is spread over six stores: PipelineRuns, Tekton Results, the release records, Testkube, Chains and Rekor, and GitHub. The only thing that joins them is Tower's backend: glidepathProvenance.ts alone is 2,994 lines with 60 routes, and four browser hooks read Tekton directly through the Kubernetes proxy. Some of that is CI/CD logic, such as working out a flow's chain slug or which releases a rollback may target, and it lives in a Backstage plugin. Clearance offers agents exactly one CI/CD tool, pipeline.rerun.

That has three costs. An agent can't ask Glidepath why a flow failed. Glidepath, which has to stay installable on its own, can't be operated without Tower. And every rule about who may promote or roll back is written in Tower's code, not in Glidepath's.

Layer 1: the contract

A new sidecar, schemas/cicd.meta.yaml, does for cicd.yaml what xrds/<kind>.meta.yaml does for an XRD. A generator folds it, the schema, the gate registry and Glidepath's state vocabularies into contract/glidepath-contract.json. CI runs the generator with --check, the same way Airframe's does.

glidepath validate checks a cicd.yaml in one pass: the schema, then GP-* rules for what a schema can't say (an environment named after a stage, a Flight environment with no release stage). With --base <ref> it also checks the GP-SCOPE rules on what changed, so the field scope below holds in CI even for a pull request that never went through Clearance. Glidepath gets an AGENTS.md and an llms.txt, as Airframe has.

Layer 2: the API

One service, glidepath-api, deployed by glidepath-control-plane on the dev cluster where the pipelines already run. Its nouns use identities Glidepath already has: a flow is one chain-id (and one Tempo trace), a release is one releaseId (<chain-id>:<cluster>/<env>), and an image is a digest. Custom verbs follow the resource:verb style.

Identity

Reuse what verifies

Pipelines and agents present a ServiceAccount token, checked with TokenReview the way the broker checks them (ADR-0002). People present an OIDC token. Tower presents tower-actor's minted token and names the user it acts for; only that subject may name someone else.

Authorization

The app's namespace is the boundary

Each call is a SubjectAccessReview against app-<name>-cicd on a virtual resource (glidepath.hangar.io flows, releases, environments) with verbs such as rerun or promote. glidepath-app renders the RoleBindings from the app's owners. No second permission model.

Every write

Plan first, once, on the record

Every write takes dryRun and an idempotency key, and records an audit event with the caller, who it acts for, the tier and the decision. A denial returns a rule id and a hint, in the shape Clearance's decisions already use.

Layer 3: tiers, and where agents come in

Agents don't get a second MCP server. Clearance registers glidepath.* tools that call the API and keeps doing what it does for every tool: profile limits, CEL rules and its hash-chained audit. The API checks permissions again itself, so a tool that bypasses Clearance is refused there too.

One rule is specific to CI/CD: an agent never satisfies a gate on its own change. A Flight change is always a pull request; the human who merges it is also who satisfies the GitHub-merge provenance check (ADR-0027). The signing policy is admin-owned and never reachable from an agent.

Agents and cicd.yaml: pull requests, limited by field

Today Clearance's BASELINE_DENY_PATHS denies cicd.yaml for every agent. That keeps agents out of their own controls, but it also stops an agent from turning on a build cache, adding a Ground environment or fixing the source volume size it was just told is too small. Even Autopilot's own planner patches cicd.yaml. The file-level deny goes. In its place is the field-level scope Clearance already uses for values files (AF-9a), with each field's class read from the contract.

The rule the old deny protected still holds: an agent never edits a control that constrains it. Secrets, signers, cloud deploy identity and the gates are those controls. A build flag isn't.

What changes in Tower

Tower keeps every route, every screen and every URL. What changes is where its backend gets each answer. Tower's backend plugin glidepath (/api/glidepath/*) gains one client for glidepath-api, and each group of routes gets a switch in config:

1

direct: today's code path, unchanged. The default for every group.

2

shadow: Tower serves the direct answer, calls the API in the background and records any difference as a metric (tower_glidepath_api_shadow_mismatch_total{group}) and a log line. Writes are never run twice. A shadowed write calls the API with dryRun and compares the plan with what Tower is about to do. This is the same live and shadow approach glidepath-relay used for ADR-0021.

3

api: the route calls the API and the direct code becomes the fallback. Going back is a config change.

Stays in Tower

Not Glidepath's

Argo CD actions (/argo/*, a delegated system). Config and values (/config, flight-base, env-xr, components, chart, platform-env: Airframe's contract). Break-glass, the cluster registry, pull requests, agent definitions.

Stays in Tower

Tower's own products

The Release Record and the release flow (/release-record*, /release-draft, /release-mode, /release-planned, /release-calendar, /release-signoff). They read release state from the API but are written by Tower. Image prune stays and reads "in use" from the API later.

Goes away in P6

Tower loses write access to Tekton

tower-actor's PipelineRun create and patch bindings on the dev cluster, the tower-pipelinerun-shape policy, the ingestor's Testkube service-proxy grant, Tower's Results cache, and the four proxy hooks. Tower then writes nothing on the dev cluster except break-glass.

RiskAnswer
The API is downUntil P6 every group falls back to direct. After P6 Tower's CI/CD views depend on the API, the way they depend on Tekton Results today. The API runs two replicas and has its own readiness alert.
The two authorization checks disagreeTower's owner check (towerAuthz.ts) keeps running in front of the API. Shadow mode also compares the API's decision with Tower's, and a mismatch blocks the cut-over for that group.
An extra hop is slowerThe Results cache Tower built in pipelineHistory.ts moves into the API: a finished run never changes. Shadow mode records how long each side takes.
Two copies drift during the moveEach group is shadowed and then cut over on its own. Only groups that are switched to api are frozen in Tower; the rest keep shipping as usual.

Roadmap

P0 · Contract, validator, field scope

Glidepath + Autopilot

cicd.meta.yaml, the contract generator, glidepath validate with GP-* and GP-SCOPE rules, AGENTS.md and llms.txt. Clearance swaps the cicd.yaml file deny for field scope from the contract. No service yet. Done when: an agent PR that turns on build.cache passes, and one that turns off governance.sast or touches secrets is refused by Clearance and fails CI.

P1 · Read API, Tower in shadow

Glidepath + Tower

glidepath-api with flows, runs, logs, releases and evidence, its OpenAPI spec, authentication and SubjectAccessReview. Tower's runs, supply chain and release-state groups go to shadow. Done when: seven days with no shadow mismatches on every app on the dev cluster.

P2 · Read cut-over, agent reads

Tower + Autopilot

Those three groups switch to api. Clearance gets the T0 glidepath.* tools. explain ships with the first knownFailures. Done when: an agent starting cold names the right failure id for a seeded failed flow, using only MCP.

P3 · T1 actions

Glidepath + Tower

Re-run, cancel, build a branch, previews, cicd:propose. Tower's run-control and cicd-editor groups go through dry-run shadow, then api. pipeline.rerun is retired. Done when: a re-run from Tower and one from an agent each create exactly one PipelineRun, and each is audited with both identities.

P4 · T2 propose

Glidepath + Tower

Promote, roll back and pin, each opened by Glidepath's release pipeline as today. Tower's promote group moves. Done when: an agent proposes a staging promotion, a human merges it, the release record reaches healthy, and the agent had no way to merge it.

P5 · Events

Glidepath + Autopilot

/v1/events and AMQP topics. An Autopilot event agent triages a failed flow and opens a cicd.yaml or code PR. Done when: a seeded failure produces a correct triage PR without anyone stepping in.

P6 · Retire the duplicates

Tower + clusters

Remove Tower's direct paths, the proxy hooks, tower-actor's Tekton bindings and the shape policy. Done when: kubectl auth can-i shows Tower's identities can't create or patch a PipelineRun.

Open decisions

Which GitHub identity opens an agent's pull request. This only matters for the content an agent writes, which is cicd.yaml and code. Promote, rollback and pin PRs are opened by Glidepath's release pipeline, as they are today.

OptionVerdictWhy
A separate GitHub App for agentsLeaningThe PR author shows it was an agent. It is installed only on the repos it needs, with contents and pull requests and never checks. Each call mints a one-hour installation token, so nothing is stored. It isn't on any ruleset bypass list, so it can't merge. This is Autopilot's D4.
Glidepath's existing bot or the Pipelines-as-Code appNoBlurs who wrote the change, and the Pipelines-as-Code app can write status checks, so an agent holding it could post a passing gate.
The person's own tokenNoCorrect attribution, but the agent inherits that person's merge rights and their token has to be held somewhere.
  • People's OIDC issuer for the CLI. Dex is already deployed. Tower doesn't need it, since it presents tower-actor.
  • Group membership for SubjectAccessReview. Tower knows a user's teams from the catalog. Glidepath standalone needs them from the token. The RoleBindings name groups either way.
  • API versioning. Proposed: copy Airframe's v1alpha1 rules. Additions are free; any tightening is a breaking change.

Not in scope

  • Argo CD control and app configuration. Those belong to Argo CD and Airframe, and Tower keeps them.
  • Any write to a Flight cluster. A release stays a gitops pull request that Argo CD syncs.
  • Replacing Pipelines-as-Code ChatOps. /retest on a PR keeps working, and the API is a second way to do the same thing.
