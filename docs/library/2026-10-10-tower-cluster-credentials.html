No long-lived Kubernetes credential for Tower, anywhere

Tower reached the dev cluster with a ServiceAccount token that never expired, copied into four places. I wanted it gone, not rotated. The spec ended up doing more than that: checking what the token could really do turned up a path to far more power than a "read-only" identity should have, and that had to close first.

Tower now holds no long-lived Kubernetes credential.

  • Federated, not stored. The dev cluster trusts the prod cluster's ServiceAccount issuer, so Tower presents a token the kubelet minted minutes ago.
  • Ten minutes at most. The trust rule refuses any token that lives longer.
  • Reads and writes are different identities. The credential in the pod can't write. A writer token is minted per action and kept only in memory.
  • A kill switch in seconds. Remove one entry from the trust file and every federated token stops working.

What checking the token turned up

Finding 0.1

"Read-only" wasn't

The token could create PipelineRuns in any namespace, and nothing constrained their shape. Chained with a privileged ServiceAccount elsewhere, that was a path to cluster-admin. Worked out from RBAC and config, never exercised.

Finding 0.2

Anyone signed in could use it

Re-run and Cancel went from the browser through Backstage's generic Kubernetes proxy, which every signed-in user could reach. That bypassed Tower's ownership check entirely.

Phase 0

Closed first

An admission policy pins the exact PipelineRun shape Tower sends. Re-run and Cancel moved to owner-gated backend routes, and the proxy now refuses anything but reads.

From a stored token to a federated one

Options considered

OptionVerdictWhy
Native federationChosenNothing stored, nothing new in the request path, the trust file reloads by itself, and claims are checked with CEL.
Secrets-store dynamic secretFallbackShort leases, but the store keeps a standing credential, and every Tower read depends on it being up.
Pinniped ConciergeFallbackSame trust model, plus a component with CA-key-level privilege. For clusters whose API server flags can't change.
A token "minter"RejectedIts bootstrap credential can mint the full-power token, so the risk stays the same.
Short-lived client certificatesRejectedSubmitting a request needs a credential first, and certificates can't be revoked.

It has to work beyond a home lab

The trust model is portable; the mechanism isn't. Managed control planes don't expose API server flags, so Tower picks how it gets a credential cluster by cluster. On the big clouds it's an exchange: the same projected token, traded for a cloud identity with a trust policy on its subject and audience. The reader and writer split carries over as two roles or two federated credentials. What gets coarser is the claim checking, and revocation is slower behind an exchange, because tokens already issued live until they expire.

The phases

One regression on the way, about 21 minutes long: a Backstage proxy quirk sent dev-cluster reads to the prod cluster once the stored token was removed. The local harness never runs in a cluster, so it couldn't have caught it. A small guard fixed it, and a cleaner fix is noted for later.
