Autopilot, drawn as Kubernetes resources

I kept describing Autopilot in words, and the words kept drifting away from the code. So I drew it the way the cluster would see it, as Kubernetes resources, and checked every box against the code on October 7, 2026. This page is that drawing. It's a snapshot, so some of what it calls a draft may have moved since, and drawing it turned up six things the code says that the docs didn't.

One Deployment, three jobs, and a grant it never hands out.

  • Clearance is the MCP server agents talk to, the policy engine that decides every call, and the keeper of each session's grant.
  • It never hands out a signed contract. It keeps the grant itself and re-checks it on every call.
  • To run an agent in the cluster it creates one AgentRun XR, and Crossplane turns that into a locked-down namespace whose pod can reach only Clearance and the model proxy.
  • On the day: Clearance's core was built and tested but not deployed. Most of the cluster side was a draft, written and unit-tested, never applied.

Six questions, answered from the code

Is Clearance an MCP server?

Three MCP tools, the rest are arguments

yes

tools_list, session_open, call. Hangar tools such as repo.pr.open or run.spawn are names passed to call, so one gate sees everything. Built on stdio; the HTTP transport isn't built.

A policy engine?

21 CEL deny rules, fail closed

yes

R000 to R020, first match wins, and any evaluation error is R000 and a deny. Tiers T0 to T3, path and field scope, repo and API allowlists, budgets. A denial returns the rule id and a fix hint to the agent.

A contract issuer and validator?

Issues a session, keeps it, checks every call

partly

There is no signed token a run carries. The grant lives in Clearance's memory, keyed by session id. Knowing a session id gives nothing: R001 checks the caller's identity against the session's principal.

Does it create the AI workload?

By creating an AgentRun, not an Agent

yes

launch (top level) or run.spawn (a child) creates the XR. Its one Kubernetes permission is a Role on agentruns in autopilot-runs. Agent is the planned XRD form of the AgentDefinition (Phase C).

Does the workload talk back to Clearance?

It's the only thing it can talk to

yes

NetworkPolicy allows DNS, Clearance and the model proxy, nothing else. The pod has two projected tokens, one per audience, valid for an hour, and no other credential.

Can outside clients use it?

And many never get a run pod

yes

Claude Code or a Tower user opens a session and calls tools with its own loop, so there is no AgentRun at all. Task, scheduled, event and team agents get one. Service agents are ordinary apps.

The map

One request, through every resource it touches. Box borders show build state. Most of the cluster side was a draft on October 7, 2026: written and unit-tested, never applied. The amber numbers are the order things happen in.

The request, step by step

1

A caller opens a session with session_open(agent, claim).

A workload definition must be called by its own service account; a delegated one must be called by a person.

2

Clearance computes the grant.

The AgentDefinition's limits, narrowed by the caller's request and, for a child, by what the parent has left. Any widening is denied (R007). The reply carries the session id, task_id, deadline and effective limits.

3

For an in-cluster run, Clearance creates one AgentRun in autopilot-runs.

Afterwards it can only patch spec.frozen (the breaker) or delete it (run.close).

4

Crossplane calls function-agentrun, which renders six provider-kubernetes Objects.

provider-kubernetes applies them into agent-r-<id>. A bad request is Rejected and renders nothing.

5

The agent calls tools at CLEARANCE_URL with its clearance-audience token.

Each call goes through authenticate, rules, audit, spend, adapter, audit.

6

Model calls go to MODEL_PROXY_URL.

The proxy checks the model allowlist and model_tokens on the same session, then forwards with a key only it holds.

7

Allowed calls reach real services through adapters.

TokenReview, the interceptor, Argo CD (lower environments only), Backstage, Prometheus, Loki, app APIs. The adapters are interfaces and fakes today.

8

Writes leave only as PRs.

The interceptor mints a GitHub token scoped to one repo for one call. Ground PRs may auto-merge; Flight PRs are propose-only and a person merges them.

9

Every decision, allowed or denied, becomes one hash-chained record with the task_id.

∎

At expiresAt the function renders nothing and Crossplane deletes the namespace, with or without Clearance alive.

A tripped breaker cuts egress and holds the run 15 minutes for forensics, then it expires.

The contract, in practice

What gets called "the contract" is a chain of five documents. The AgentDefinition in git is the ceiling. Every later copy can only narrow it, and only the session inside Clearance is checked on each call. The copies in the AgentRun and the pod are for information, except the deadline, network mode, compute and sandbox, which the composition enforces on its own.

Does it hold the budget? Yes

The session holds six limits: the TTL plus five counters (tool_calls, github_calls, open_prs, model_tokens, children), and spends them as calls happen. A child run reserves its budget out of the parent's remainder when it starts, and its real usage rolls up when it closes, so a team can never spend more than its root was granted. A 200-sequence property test covers this.

Five denied calls, a tripwire, or a token overrun trips the breaker. The counters exist only in Clearance's memory: a restart ends every session, which is the safe direction, and the runs still stop on time.

The acceptance test: the parachute sentence

"Provision a new python application named parachute. Give it a dev and test ground environment, a staging and prod flight environment, and configure it with one 100% weight canary step and a URL=http://myendpoint.io env var."

  • A person says it to a coding agent, in Tower chat or in Claude Code (step 1). The session gets repo.pr.open, xr.request, repo.pr.open_upper and the airframe.* tools.
  • The agent writes the AppSpec below and calls airframe.plan. The planner, inside Clearance, compiles it into an ordered ChangeSet with no network and no clock, so the same input gives the same plan.
  • airframe.apply walks the plan as PRs (steps 7 and 8). Each step's tier decides the gate: Ground and tenants work is T1, Flight values are T2 propose-only.
  • A person merges the Flight PRs. Argo CD and Glidepath do the rest, and airframe.verify checks the result.
  • Every step is on the record under one task_id, so a killed session can resume from the PR labels and the log.

The planner raises two warnings on its own: the environment name test collides with the pipeline stage name, and a single 100% step promotes at once with no ramp. The app-repo row is where the plan broke on October 7, 2026; see the first two gaps below.

The flight recorder

Clearance writes one record per decision, allowed or denied, chained to the one before. Arguments are kept only as a hash, so a secret that slips into a call never lands in the log. The chain proves nobody edited, deleted or reordered records. It can't prove nobody cut off the tail, which is why the checkpoint gets anchored in Rekor and copied to an object-locked bucket.

Found while drawing this

Six things the code said that the docs didn't. Each was checked against the autopilot repo on October 7, 2026, not taken from the docs. I haven't rechecked them for this page, so treat each as found on that day.

The parachute plan is denied by Clearance's own baseline.

Found Oct 7, 2026

Blocks M3 exit. The planner's app-repo step patches cicd.yaml. BASELINE_DENY_PATHS puts cicd.yaml off-limits to every agent, and test_dispatch.py asserts that exact denial (R015). Run end to end, the sentence stops at step 3. This needs a decision: a field-level allow for /deploy/environments using the AF-9a machinery, or hand that step to a person through Tower's existing cicd.yaml PR flow.

The planner is stale against the environments overhaul.

Found Oct 7, 2026

1 test failing. 234 of 235 tests pass. The failure: the planner emits deploy.lowerEnvironments, upperEnvironments and promotionOrder, and Glidepath's schema now accepts only deploy.environments (ADR-0019). It also writes platform/envs/*.yaml, while apps now use glidepath/envs/.

A run pod can't pass R001 yet.

Found Oct 7, 2026

Design gap. R001 compares the caller with session.principal, which is the person or the definition's service account. A run pod authenticates as system:serviceaccount:agent-r-<id>:run. Nothing maps one to the other. The unbuilt auth adapter has to, for example by finding the AgentRun that owns that namespace and taking its sessionId.

The recorder can't reconstruct what a run was allowed to do.

Found Oct 7, 2026

Audit gap. The session.open record stores the caller's request only as a hash and doesn't store the effective limits, and sessions live only in memory. After a restart the grant is gone. The limits hold no secrets, so recording them in that record costs nothing.

The drafts still used the old API group.

Found Oct 7, 2026

Drift. manifests.py and the AgentRun XRD said catalog.idp.io; the Tier 2 rename had moved everything to catalog.hangar.io, and design.md's Role already used the new group.

The counts in the docs were out of date.

Found Oct 7, 2026

Docs. The docs said 19 CEL rules and 255 tests. The code had 21 rules (R000 to R020, with R020 for field scope added by AF-9a) and 235 tests.
