Any forge, any registry

A plan to run Hangar on GitLab and Bitbucket as well as GitHub, and to publish images to any OCI registry as well as GHCR, without changing what Hangar is.

Scope: Airframe, Glidepath, Tower and Backstage, Apron, AutopilotBasis: origin/main of every repo, the live dev clusterStatus: proposal, for decision
Feasible · 6 phases · about 24 weeks

The engine is already neutral. Three things are not.

Tekton, Pipelines as Code, Argo CD, External Secrets, Crossplane and cosign all work with GitLab and Bitbucket today. GitHub is wired into Hangar in about a hundred small places (a literal owner, a curl to api.github.com, a hardcoded link), and in three places it is part of the design:

  • The control plane writes to repositories through provider-upjet-github. 81 templates in 9 compositions, 88 live resources on the dev cluster. The GitLab provider has no file resource and no maintained Bitbucket Cloud provider exists, and this provider caused the September data loss and rate-limit storms.
  • CI tokens are GitHub App installation tokens. The never-persisted credential model is built on a GitHub feature that GitLab and Bitbucket do not have in the same form.
  • An app is identified by github.com/project-slug. Tower authorization (ACC-05), release approvers and the catalog app list all key on it, and it assumes a one-segment owner that GitLab subgroups break.

Recommendation. Introduce two Hangar-owned contracts, one for the forge and one for the registry, with each vendor as a driver behind one of them. Move the existing GitHub path onto the contracts first, with no visible change (phases 0 to 2, which also removes the RepositoryFile bug class on GitHub). Then add GitLab as the proof (phase 3) and Bitbucket after it (phase 4). The forge and the registry become separate choices, because a Bitbucket shop has no registry of its own.

Principles

Separate the forge from the registry

Choose them independently. The image path comes from registry config, never from the forge owner.

Hangar names things

scm.hangar.io resources, hangar.io/app identity, an scm CLI. Vendors are drivers.

GitHub moves first

Nothing reaches GitLab until the GitHub path runs on the contracts with no change a user can see.

Capabilities, not the lowest common denominator

A driver declares what it can enforce. Tower shows the real level per app.

Write the credential delta down

Every forge gets a row in the credentials table. Weaker is allowed; silent is not.

Adopt, never recreate

Every migration step observes existing repos by name. No step may commit or delete.

Target architecture

The SCM contract has two faces over one Go library:

  • Declarative: provider-hangar-scm, a native Crossplane provider serving scm.hangar.io/v1alpha1 Repository, RepositoryFile, Webhook and MergeGate. A ProviderConfig per forge instance (github, gitlab) picks the driver, so each composition keeps one shape and only its providerConfigRef changes. RepositoryFile.spec.mode is seed (create once if absent, never update or delete: today's scaffold rule, written into the API instead of into management policies) or managed (the platform-owned identity files in tenants repos).
  • Imperative: an scm CLI in the Glidepath toolbox image (scm pr open|find|comment, scm status, scm contents get, scm compare, scm pr-for-commit, scm gate apply) that replaces the inline curl, and a broker endpoint /scm-token beside today's /github-installation-token.
  • Tower gets a TypeScript ScmClient and RegistryClient in the Backstage backend, with drivers built on @backstage/integration, which already resolves credentials for GitLab, Bitbucket Cloud and Bitbucket Server. It runs the same recorded conformance fixtures as the Go library.

The registry contract is mostly plain OCI. Push, pull, digest, tags, referrers and cosign signatures work against any compliant registry with the standard bearer-token challenge, so the GHCR-specific token exchange in ghcr.ts goes. Only listing versions with dates and deleting them are vendor APIs, so only those need drivers. Config is registry.host and registry.namespace; the image path is <host>/<namespace>/<app> and previews add -pr.

Identity. Add hangar.io/app (the app's Hangar name), hangar.io/forge and hangar.io/source-location. Tower authorization reads hangar.io/app; GitHub apps keep github.com/project-slug for stock Backstage plugins. A repo's namespace may have several segments (GitLab subgroups, a Bitbucket workspace and project).

Sign-in. Move Backstage from GitHub OAuth to OIDC through Dex, which already runs in the cluster and has GitHub, GitLab and Bitbucket Cloud connectors (LDAP or SAML for Data Center shops). Users still match catalog Users. This also moves the architecture review's SSO gate forward.

The proof: one release on GitLab

What changes, product by product

Airframe

  1. Every repo.github.m.upbound.io template becomes scm.hangar.io; the symlinked _shared partials keep the diff small.
  2. Owner, host and registry come from the cluster registry entry (already read through ExtraResources), never a literal.
  3. Optional spec.source (forge, namespace) on app XRDs, defaulted from platform config; CEL checks the namespace shape per forge.
  4. A Webhook per repo on forges without app-level webhooks; the Go module path follows the source host.

Glidepath

  1. The scm CLI replaces curl, one Task per PR, each with fixtures. ADR-0026: the SCM contract.
  2. platformIdentity.githubOwner becomes platformIdentity.source; image-repo comes from registry config.
  3. The broker gains /scm-token and the PaC secret rotator; PaC Repository CRs gain git_provider off GitHub.
  4. github-ruleset.md becomes merge-gate.md; scm gate apply renders it from releaseGuardrails.

Tower and Backstage

  1. ScmClient and RegistryClient; today's GitHub code becomes the first driver, unchanged.
  2. Authorization and approvers read hangar.io/app; links come from hangar.io/source-location.
  3. Integrations, scaffolder publish actions and the ingestor publish target per forge; sign-in through Dex.
  4. Each app shows its forge and the merge-gate level the driver reports.

Apron, Autopilot, Hangar

  1. cluster.yaml gains scm.forge, scm.namespace and registry.*; the script renders repo creds, the PaC secret and the allowed SCM providers per forge.
  2. provider-github is removed after phase 2.
  3. Agent images come from registry config.
  4. Business rules PPL-01, PPL-02, ACC-05, GATE-03 and GATE-06 are reworded per forge when each lands (docs/policy/business-rules.md).

Moving the GitHub fleet first

Roadmap

P0

Seams, GitHub only. No api.github.com or ghcr.io literal outside a driver, enforced by a CI ratchet; no owner literal in compositions; Tower reads hangar.io/app.

Exit, live: a Skyport release and rollback behave exactly as before; GitHub calls per hour at or below the baseline.

P1

Registry independence. Image path from config; a second registry lane.

Exit, live: one Skyport app builds, signs, passes the provenance gate, deploys, lists and prunes from a non-GHCR registry.

P2

provider-hangar-scm. GitHub driver, then adopt all 88 live resources and uninstall provider-upjet-github.

Exit, live: zero commits during adoption; an injected 403 rate limit neither deletes nor rewrites a file.

P3

GitLab end to end. Drivers, broker, PaC, Argo CD, Backstage, Dex.

Exit, live: figure 4 runs with a rollback; the merge gate refuses a red gate; broker tokens are revoked after each run.

P4

Bitbucket. Cloud first, then Data Center, with Harbor.

Exit, live: the phase 3 test on Bitbucket Cloud.

P5

Mixed fleet. Per-app forge, rate budgets per forge in Grafana, docs, business rules, scorecard.

Exit, live: one fleet with apps on two forges.

Decisions for you

D1

How the control plane writes to a forge

Recommend option C, provider-hangar-scm, in Go. The Python preference for composition functions does not apply to a provider.

D2

Order of forges

GitLab, then Bitbucket Cloud, then Data Center. GitLab has the closest feature set and its own registry; Data Center needs a licensed server for the lab.

D3

Where the GitLab lab lives

A gitlab.com Free group. The prod cluster has no CPU to spare for self-managed GitLab. Free has no required approvals, so the two-person rule stays "Off here", as on GitHub Free today.

D4

The second registry

GitLab Container Registry for the GitLab lane (no infrastructure), Harbor as the documented neutral default, run in CI.

D5

Accept the credential differences

Accept, with revoke-at-end and daily rotation, and Tower showing token age. Bitbucket Cloud's workspace-wide token is the one to watch.

D6

One forge per fleet, or per app

Fleet default through phase 4; the per-app field is in the schema from phase 0 but enabled in phase 5.

D7

A name for the SCM component

Yours to choose, in the aviation vocabulary. Working name: hangar-scm.

Risks

  • Rate limits. Bitbucket Cloud's hourly API budget is far smaller than GitHub's, and the old fleet once burned 16,000 calls an hour in a loop. Seed files are never re-read after the scaffold ledger marks them done; every driver uses conditional reads where the forge supports them; a per-forge budget metric trips a breaker.
  • Nested namespaces break every owner/repo parse: Tower's split('/'), the broker's name match in verifyAppOwnsRepo, Glidepath's git-url handling. Phase 0 fixes them on GitHub.
  • Webhooks per repo mean more objects and more secrets; each is an scm.hangar.io Webhook with its own rotated secret.
  • Test matrix. Four forges and four registries. Recorded conformance fixtures run on every PR; one live lane per forge runs nightly.
  • Plan tiers change what is enforced. Tower reports the level the driver measured, never an assumed one.
  • Owning a provider is code to maintain, set against retiring one that needed a fleet-wide pause.
