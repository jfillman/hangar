Glidepath · Spec · Testing and the QA gate

A test contract for Glidepath, and a QA gate that reads it

Glidepath already ran a TestWorkflow and the release stage already had a slot for a QA gate. The question was whether that is enough: give the business a standard test, give developers the implementation, and let the gate read the result. Reading the code and the live cluster, the answer was nearly yes. Three things were missing, and none of them is a test runner.

Since then. Phases 0 to 3 were built in Glidepath and verified live on boarding-api by October 19, 2026, with the real qa gate reading the check ride from the image's test provenance. Phase 4 shipped the same day in Tower v0.79 and v0.80: test evidence on the image and the Release Record, check-ride readiness and a Tests view under Pipelines. The reference for what is built is Glidepath's testing doc; this page is the proposal as written.

Keep the wrapper · add the contract · attest the result

Glidepath should stay a thin wrapper around Testkube. What it must own is the contract, the evidence and the fence.

  • The contract. What the wrapper passes into a workflow (image, digest, environment, URL) and what it records out (a fixed result set, tags on the execution, JUnit counts). Today it passes nothing in and records two strings out.
  • The evidence. A signed check-ride attestation on the image digest, made the same keyless way sast-scan already attests. The QA gate then verifies, with cosign and Rekor, instead of querying a database it has to trust.
  • The fence. A shared repository of check-ride templates and per-app workflows, synced into Testkube by Argo CD, with code owners from both SDETs and the app team. The business sets the standard in the template; the team writes the steps.
  • Everything else a test platform needs (reports, retries, matrix, services, schedules, a viewer) Testkube already provides, including in the free agent. Glidepath should not rebuild any of it.
Found live · Oct 17, 2026

No Skyport app runs a test. The whole path from test step to Release Record has had no consumer since the demo apps were retired.

baggage-api, boarding-api, gate-api and sky-marshall all declare build → deploy test → deploy dev with no test step and no TestWorkflow file. The only TestWorkflows in the testkube namespace are two one-step curl smoke checks from demo apps that no longer exist, last executed 42 days ago. Tower's Release Record reads test results from Tekton Results and finds none, the qa gate is a declared stub, and Autoland is parked on "needs real test results". Every finding below was read in source, then checked against that cluster.

What is there today

The wrapper is better than its reputation. run-testworkflow is careful about secrets, names, the CLI's log-streaming bug and Testkube's false-abort race, and it already emits a result and an event. What it lacks is a reason to exist: no app calls it, nothing it produces is addressed to the release, and the gate that should read it reads nothing.

Is a wrapper plus a contract enough?

Yes, with one addition. A wrapper decides what goes in and what comes out; that is the contract. But a gate that reads a contract from a database has to trust the database, the namespace it lives in, and whoever can write to it. The release stage already solved that problem once for SAST: the build attests, the gate verifies the signature against the platform's own Fulcio and Rekor. The test stage should do the same. Then the contract has two halves, and the gate needs no new trust.

Glidepath owns

The contract

A fixed set of inputs every workflow can rely on (config and tags: app, image, digest, env, URL, revision, chain) and a fixed set of outputs the platform records (outcome, execution id, workflow revision, JUnit counts, report link). Three step roles: execute, test, check ride.

Glidepath owns

The evidence

After a passed check ride, the wrapper signs a check-ride attestation onto the image digest, keyless, as the app's own pipeline-runner. The attestation travels with the image to every cluster and outlives every archive. The qa gate verifies it.

Glidepath owns

The fence

A shared check-rides repository: templates owned by SDETs and product, per-app workflows owned by the team and SDETs, synced by Argo CD into the testkube namespace, and admitted by the existing Kyverno policy extended to cover synced workflows.

Testkube owns

Running tests

Templates with typed config, step retries and timeouts, services and matrix runs, JUnit parsing, artifacts, schedules, webhooks and CDEvents, the execution record and a viewer. All in the free agent. Glidepath calls these; it does not rebuild them.

The design

Four changes to Glidepath, one new repository, one new attestation type, and a Tower strip. No new stage, no new CRD, no new service.

Test and execute steps

Keep stage: test as the only DAG slot; the fixed superset DAG is a design rule worth keeping. Give the step a role that says what kind of thing it is, and pass the step's context into the workflow instead of applying the file blind.

role: execute

An action, not a test

Clear a cache, warm a pool, seed a fixture, run a migration dry-run. Pass or fail still chains the next stage. No attestation, no JUnit expected, no QA evidence. A missing workflow is a failure, since the step was written on purpose. required: false turns a failure into a warning for best-effort actions.

role: test (default)

The team's own tests

Integration, contract, smoke, load. The workflow lives in the app repo as today. Results are recorded and shown, and the next stage chains on them, but the qa gate does not read them. A missing workflow is a failure.

role: check-ride

The standard the release depends on

The workflow is <app>-check-ride from the shared repository, never from the app repo. Its passing run is attested onto the digest. Exactly one per flow, and validateFlows requires one after the last Ground deploy in any flow that ends in a release, once the catalog switches qa.required on.

cicd.yamlWhat it means
pipelines: ci: trigger: { source: git, event: push, branch: main } steps: - stage: build - stage: test env: dev testName: flush-cache role: execute required: false - stage: deploy env: dev - stage: test env: dev testName: integration # glidepath/integration.yaml timeout: 20m - stage: test env: dev role: check-ride # <app>-check-ride, shared repo - stage: release env: staging

One flow, three test steps with three meanings. The execute step runs before the deploy and may fail without stopping the chain. The test step is the team's own suite, with its own time budget (the fixed 60 × 10 s loop becomes a parameter). The check-ride step takes no testName: the platform knows the name. Each step's trigger is already distinct by index, so nothing changes in the flow triggers.

Every step, whatever its role, runs the workflow with the same config and tags: app, image, digest, env, url (the Ground service address, http://<app>.app-<app>-<env>.svc), revision, chain, step. A workflow reads them as {{ config.url }} and never hardcodes an environment.

Unchanged: the env requirement, the chain on outcome == Succeeded, the secrets materialization, the name rewrite to <app>-<name>, and the false-abort workaround. Ground only for now: a check ride against a Flight environment needs a trigger on release healthy, which does not exist yet (roadmap phase 6).

The check-rides repository

A check ride is the flight test a pilot passes to be certified for a rating. Here it is the one workflow a release must pass, and the name separates it from the team's own tests. The repository is the shared ground: the business sets the standard in a template, the team implements it in a workflow that uses the template, and GitHub code owners make both signatures necessary.

Sync

Argo CD, not the pipeline

One Application in gitops-cluster-dev syncs templates/ and apps/ into the testkube namespace. The pipeline no longer applies a check-ride workflow; it runs the one that is there, and records the synced revision. A developer cannot run a hollow local copy and call it the check ride.

Fence

Kyverno, extended

ADR-0008's policy keys the allowed secret on the caller's namespace, which works for pipeline-runner and not for Argo CD. Add a rule for the sync identity: a workflow it applies may reference only the secret of the app named in its hangar.io/app label, and the label must match the file's apps/<app>/ folder. Same policy file, one more rule, live-verified with kubectl --as as before.

Shape

Template sets the floor

The template declares the steps every service must pass and marks them as not optional. The app's workflow adds steps and fills config. Testkube merges them, so the team cannot remove a required step without changing the template, which needs the product owner.

The contract

Three records, written in one place (run-testworkflow) with the same fields. The attestation is the one the gate reads. The Task results are the ones Tower reads today. The CDEvent is the one the broker and any future subscriber reads. Keeping them identical is the whole point: one definition, three carriers.

Predicate type

https://hangar.io/attestations/check-ride/v1

An in-toto statement whose subject is the image digest. Signed keyless by the app's pipeline-runner through the in-cluster Fulcio, uploaded to Rekor, the same path and the same verification identity verify-sast-attestation already checks. Written only for role: check-ride and only on a pass; a failed check ride leaves no attestation and the gate fails for want of one.

Tags

Found by image, later

Every execution carries app, image, digest, env, role and chain as Testkube execution tags. Tower can list an app's runs with one tagSelector query, and the gate's PR comment can link to the execution it verified.

Fail, don't skip

Skipped is for disabled, only

outcome: skipped stays for test.enabled: false. A step whose workflow does not exist fails. A check-ride step whose synced workflow is missing fails with "no check ride for <app> in the check-rides repo", which is the onboarding message a new app needs.

The qa gate

Landing the real gate is the one-file change qa-gate.yaml was shaped for: replace the stub step with verify-and-check, flip the registry entry to real, add the check to the ruleset. The PR comment carries the counts and the link, and the Release Record freezes the same evidence.

Risks and open decisions

Decision

Ground evidence for a Flight release

Phase 3 accepts a check ride run on the last Ground environment as evidence for the first Flight PR. That is the honest floor today: nothing can trigger a test on release healthy. The production PR should eventually require a run tagged env=staging. Decide whether that is a gate rule (fail) or a readiness row (display) when phase 6 lands.

Decision

Where check-ride content comes from

A check ride tests the running service, so its steps should come from the shared repo and its target from config. If a team's suite lives in the app repo, the workflow pulls it with content.git at the revision under test. The template decides which is allowed; recommend: steps from the shared repo, suites from the app repo.

Risk

GitHub Free

CODEOWNERS and the qa check both report without blocking on a private repo. The check-rides repo can be public (no secrets), which makes its ownership real now. The gate waits on T1 like every other gate.

Risk

Attestation sprawl

Every passing check ride adds an attestation to the digest; a digest rebuilt and retested ten times carries ten. cosign handles many; the gate takes the newest that verifies. Prune with the image prune Tower already runs.

Risk

The shared namespace is still shared

Synced check-ride workflows and team workflows sit in one namespace. The Kyverno rule keeps secrets apart; nothing keeps a team's workflow from naming itself other-app-check-ride except the name rewrite in the wrapper and the folder-to-label rule in the sync policy. Acceptable for one owner's apps, as ADR-0007 says; revisit with Pro or a second Testkube.

Risk

Testkube version

2.12.2 is from early September. The false-abort race, the reports field and CDEvents emission should all be re-checked on the version phase 0 pins. Upgrade first, then build on the fields.

Roadmap

Six phases in order, each with a test that says when it is done. Phase 0 is the cheapest and the most important: nothing in this design should be built before one real test has been seen to run and fail on the cluster. Phases 1 to 3 are Glidepath; phase 4 is Tower; phase 5 is rollout. Effort is a single-engineer estimate.
