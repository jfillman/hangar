Airframe, the service catalog under Hangar

Airframe is the Crossplane-based service catalog behind Hangar. Eleven XRDs turn a git commit into a running service that is onboarded to CI/CD and has its secrets, without any cluster ever holding credentials for another cluster's API. I drew this on September 20, 2026 to see the wiring underneath: what each catalog object takes in and gives back, how the pieces compose, and what actually moves when someone asks for a service. It's a snapshot. The design doc is the living version, and it has moved on since.

Snapshot · Sep 20, 2026

Everything routes through git.

  • Airframe has no API server and no webhook receiver. A request to the catalog is a commit: a manifest written into a tenant's xr-requests/ folder.
  • Argo CD is the only thing watching that commit, and Crossplane is the only thing allowed to act on what Argo CD syncs. Repos, CI/CD onboarding, secrets and the running workload are all side effects of that one XR existing on a cluster.
  • The engine stays on one dev cluster, because its only two levers, provider-upjet-github and a GitOps commit, never need a credential to any other cluster's API.

The shape of a request

The trust boundary

Git-only, on purpose

Airframe holds exactly one live credential class: a GitHub personal access token for provider-upjet-github and, for secrets, an Infisical identity. It never authenticates to a second cluster's Kubernetes API. Every cross-cluster effect happens by committing a file into that cluster's own tenants repo and letting its own Argo CD pick it up.

Every cluster

Two Argo CD instances

argocd-platform is cluster-admin and installs the catalog itself. argocd-apps faces app owners, with one AppProject per app. The sets of repos they watch never overlap.

The loop

Why the write loops back

The engine's own Composition writes the very manifests Argo CD will later sync: identity.yaml, the release values.yaml, a SecretStore request. It closes the loop through git instead of calling any API directly.

The catalog: eleven XRDs, one composition graph

An app is created from one of five Bootstrap-tier stacks. Every stack composes a TektonCICD child directly. That's a normal in-process composition, and it's safe because TektonCICD only ever calls the GitHub API. Everything that has to land on a different cluster's API, namely SecretStore, is requested the indirect way: a commit into that cluster's own xr-requests/, never a direct composition.

Three tiers, three lifecycles

The tier isn't a UI grouping. It's the mechanism. Bootstrap-tier XRs are created by a git commit and never touch a live cluster API, which is exactly why the engine can stay on one dev cluster however big the fleet gets. Attached-tier XRs compose real in-cluster resources directly, so they only mean something where Crossplane is actually running, and they have to be created per cluster.

From request to running service

One trace, start to finish: a developer asks for an app and an environment, the engine writes the git state that makes both real, and the target cluster ends up running a workload.

What each Composition actually calls

Every Composition in the catalog is a function-go-templating pipeline with inline source, plus a function-auto-ready step. The source stays inline because a second registered Function package once corrupted Crossplane's shared dependency-lock graph across the whole cluster. Below that shared shape, each XRD reaches a different real system.

GitHub

provider-upjet-github

The namespaced managed-resource family (repo.github.m.upbound.io), with a personal access token, because a GitHub App can't create repos under a personal account. It creates Repository and RepositoryFile resources: the src repo, its boilerplate, the empty gitops-<app> repo, identity.yaml and the release values.yaml. As of Sep 21, 2026 the boilerplate includes a real, build-only cicd.yaml, which closed the one hand-written step in an otherwise self-service flow.

Secrets

provider-infisical and ESO

Project, ProjectEnvironment, Identity and ProjectIdentity managed resources, wrapped through provider-kubernetes into a real ESO ClusterSecretStore. Crossplane v2 forces the wrap, since a namespaced XR can't compose a cluster-scoped resource directly. Kubernetes Auth on the cluster that hosts Infisical, Universal Auth everywhere else.

Compute

provider-helm

Redis composes a Release of a Bitnami-derived chart. It was the only component XRD with a real workload behind it. Every other planned component (Postgres, RabbitMQ, MongoDB, OAuthServer, nginx) was unbuilt.

Observability

Sloth and HolmesGPT

SLO renders a Sloth PrometheusServiceLevel, which Sloth's own controller turns into a real PrometheusRule. RolloutWatch finds the live Rollout through a Crossplane extra-resources lookup and, when it goes Degraded, sends a diagnosis Job to that cluster's HolmesGPT service, which can open a fix PR back into the GitOps repo.

"No cluster ever holds credentials for another cluster's API."

That one rule explains every indirection on this page: why SecretStore goes through a GitOps commit instead of a direct composition, why the Bootstrap engine can stay on one dev cluster for good, and why each cluster's own argocd-apps is the only thing that ever touches that cluster's workloads.

Not yet live on September 20, 2026

Don't read these as built. Check the living design doc for where each one stands now.

  • OAuthServer, Database (postgresql), Queue (rabbitmq), mongodb, nginx. Zero XRDs existed.
  • BranchProtection. Deliberately deferred; it needs real CI status-check names.
  • Platform default canary steps. The chart shipped an inert single-step placeholder.
  • A ClusterAnalysisTemplate golden-path library. It belongs in the cluster baseline repo and wasn't built there.
  • A second real dev cluster. The registry gate existed; nothing had exercised it.
  • The environment deletion and Argo CD prune deadlock. Downgraded to monitor-only, not proven resolved.
